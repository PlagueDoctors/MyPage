### 现状代码的关键缺陷（写进方案的诊断结论）

P0：
1. **帧率耦合** — `:379` `progress += velocity` 无 dt 归一化（144Hz 跑 2.4 倍速），
   而隧道位移却硬编码 `* 0.016`（`:391`），只修了一半
2. **`deltaMode` 未归一化** — `:304` Firefox 按行(≈3)/Chrome 按像素(≈100)，差约 30 倍
3. **三处真相源** — HTML `data-start/end`、`MODEL_CHAPTERS`:19、`CHAPTER_BOUNDARIES`:17
4. **JS 失败 = 全黑屏** — `overflow:hidden` + `preventDefault` + `.chapter{opacity:0}`
5. **CDN 单点** — unpkg 运行时依赖；`import * as THREE` 让 tree-shaking 失效

P1：
6. **CPU 逐帧变形** — `:355-374` 每帧 4000 次对象字面量分配（`rotateTarget` 返回 `{x,y,z}`）
   ≈ 24 万临时对象/秒；`needsUpdate` 触发整块缓冲重传（48 KB/帧）
7. `:400-408` 冗余全量拷贝分支
8. `:278-291` 逐帧 `Number(dataset.start)` 字符串解析
9. `css/experience.css:98` transition 与逐帧写入打架
10. 只有 `FogExp2(0.000008, 0.012)`，黑场景下雾不可见 → 无景深
11. `:104-127` 采样**按顶点而非按面积** → 密度正比于网格细分而非表面积 → 轮廓破碎

P2：

15. 末章淡出区间落在 `progress=1` → **最后一屏是空的**（结尾感消失）

### 方案要点（目标架构）

- **技术选型**：Vite 5+ / TypeScript / Three.js(npm) / **原生滚动 + 阻尼插值**（替代飞轮）/
  自研 40 行 scrubber（不引 GSAP）/ 自定义 `ShaderMaterial`
- **单一配置源** `src/config/chapters.config.ts` + dev-only `validate.ts` 断言
  （区间连续、hold ⊂ range、末章淡出早于 `range[1]`）
- **GPU 点云着色器**：`mix(position, rotate(aTarget))`，每帧只写 4 个 uniform，O(1)
- **伪景深**：`coc = |depth - uFocal| / uFocal` → 尺寸放大 + alpha 衰减
- **滚动 warp**：把物理滚动重映射到时间轴，停留段占 70% 滚动距离
  —— 从结构上取代 `SENSITIVITY_IN_CHAPTER/TRANSITION` 那套 hack
- **面积加权 + 重心坐标采样**（`r1 = sqrt(rand)`），离线构建成 Int16 量化 `.bin`
- 7 个阶段（Phase 0–6），每阶段可独立上线

### 值得记住的技术坑（可复用）

- **`gl_PointSize` 有硬件上限**：`ALIASED_POINT_SIZE_RANGE`，桌面常见 1024，
  但 **ANGLE / 移动端常被钳到 63 或 64**，超出静默截断 → 景深在移动端失效且难定位。
  必须运行时查询并 `min(max, 64)` 写入 uniform。
- 帧率无关阻尼公式：`a + (b - a) * (1 - Math.exp(-lambda * dt))`，并 `dt` 钳制上界
  防止切回标签页时过冲。
- **点云不要用 Draco**：Draco 为三角网格设计；位置数组直接量化 Int16 +
  `setNormalized(true)` 即可，更小更快，且省掉 WASM 解码器。
- 离屏采样后运行时无需 GLTFLoader → 可评估用自研 WebGL2 渲染器（约 15 KB）替换
  Three.js（约 330 KB gz）。
- 不要用 CSS `scroll-snap` 配阻尼插值 —— 二者争夺同一个 `scrollY`。

### 离线点云管线（`tools/build-pointcloud.mjs`）

### 关键实现要点（后续维护须知）

1. **`warp()` 取代 `SENSITIVITY_*`**：`timeline.ts` 的 `HOLD_SCROLL_BOOST = 1.45`
   是手感主旋钮；`.scroll-track` 每章 135vh 是第二个入口。
2. **帧率无关阻尼** `1 - exp(-λ·dt)`，所有随时间的量都乘 dt。
3. **着色器里 `uSizeScale = drawingBufferHeight / (2·tan(fov/2))`**，
   于是 `uSize` 是纯粹的世界空间直径，与画布/dpr/fov 解耦 —— 换设备不用重调参数。
4. **`uFocal` 直接取相机到注视点的距离**，焦平面自动跟着每章形状走，无需手工配对。
5. **`aMorphWeight`**：30% 粒子恒不聚合，永远留在环境里。没有它形状一成形背景就空了。
6. **`burst = m(1-m)·4`** 让过渡扰动在中段最强，首尾安稳。
7. 加色混合 + `depthWrite:false` → **无需深度排序**。
8. 切换形状时**只换 `BufferAttribute` 引用**，零拷贝；只在 morph≈0 时触发。

## 第三轮（同日）：线上空白页事故与修复

**用户报障**：「GitHub 上的 deployments 页面无法显示动画了」。

### 根因（不是渲染 bug，是部署管线缺口）

用户已把我的改动提交并推送为 `16c5407 refactor 1.0.0`。但：

- **仓库里没有 `.github/` 目录** → 没有任何 CI
- GitHub Pages 当时是 **Deploy from a branch → main / (root)**，即**直接发布源码目录**
- 而新的根 `index.html` 是 **Vite 的源码入口**，引用 `/src/main.ts`

于是浏览器请求 `/MyPage/src/main.ts`，GitHub Pages 以非 JavaScript 的 MIME 类型返回，
**模块脚本被拒绝执行 → JS 从未运行**。而章节文案完全由 JS 从 `chapters.config.ts` 渲染，
所以页面是一片黑（只有静态的 `#hint` 与 `.corner-link`）。

旧版能"正常工作"纯粹因为它是**无需构建**的纯 HTML/CSS/JS，直接提交到根目录即可。
Phase 0 引入了构建步骤，但我**漏了配套的工作流** —— 是我的疏漏。

这也暴露了我此前那条"静态可读是 CSS 默认态"的防线有个盲区：
它挡的是"JS 执行失败"，挡不住"模块脚本压根没被加载"。

### 修复内容（已提交 `bfeb180`）

1. `.github/workflows/deploy.yml`：`npm ci → typecheck → build → upload dist → deploy-pages`
2. `index.html` 增加**内联引导看门狗**：模块脚本一旦执行，`main.ts` 立刻置位
   `window.__mypageBooted = true`；3 秒后仍未置位就把排查说明面板显示出来。
   把"无声黑屏"变成"能自我说明的页面"。
3. `public/.nojekyll` 防止产物被 Jekyll 处理
4. README 的部署章节改写（原来还写着 `gh-pages` 分支，已与新流程不符）

  Settings → Pages → Source = GitHub Actions
  等效命令：`gh api -X PUT repos/PlagueDoctors/MyPage/pages -f build_type=workflow`

| 检查 | 结果 |

### 结论

**`deploy-pages` 报告成功 ≠ 站点已更新。**

当 Pages 的 Source 是 `Deploy from a branch` 时，GitHub 会：
1. 仍按分支构建跑一条 `pages build and deployment`
2. 同时允许 `deploy-pages` 创建 deployment（所以 job 显示 success）
3. 但**分支构建最后落地**，把站点覆盖回源码目录

于是出现最阴险的状态：**所有指示灯全绿，站点却是坏的**。
判断依据就是那条 `pages build and deployment` —— 它只在 legacy 模式下才会运行。

### 修复

**唯一需要的动作**：Settings → Pages → Build and deployment →
**Source 改成 GitHub Actions**（一次即可），然后重新运行工作流。

在 `deploy` job 的部署步骤之后加了一步冒烟测试：
拉取 `steps.deployment.outputs.page_url`，断言 HTML 里含 `assets/index-`；

**意义**：把「全绿但站点是坏的」这种静默失败，变成一次指名道姓的红灯。

## 第五轮：冒烟测试假阳性 —— 我加的第一版防线是坏的

用户再次贴出同一段面板文本。复查远端发现：

- `a5ba7bd`（我最新两个提交）**已被用户推送**
- 新的 `Deploy to GitHub Pages`（`a5ba7bd`）**success**
- 而且 **`Smoke test` 这一步也是 success** ← 但它本该报红
- 同一个提交上 **`pages build and deployment`（event = dynamic）又跑了一次**
- 线上仍是 `/src/main.ts`，`assets/`、`pointcloud/`、`.nojekyll` 全 404

### 假阳性的两个原因（都是我的疏漏）

1. **`curl` 少了 `-L`**
   `steps.deployment.outputs.page_url` 不带尾斜杠，拼上 `?cb=` 会触发 301，
   curl 不跟随就拿不到正文。
2. **没有静置**
   Source 是 legacy 时，GitHub 并行跑的 `pages build and deployment` 可能**在
